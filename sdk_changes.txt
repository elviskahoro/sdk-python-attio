# SDK Changes for Timestamp Value Fix

## Problem
The SDK was generating validation errors when unmarshalling API responses that contained timestamp values. The error was:

```
53 validation errors for Unmarshaller
body.values.created_at.0.PostV2ObjectsObjectRecordsValueTimestamp.value
  Datetimes provided to dates should have zero time - e.g. be exact dates [type=date_from_datetime_inexact]
```

This occurred because the Speakeasy code generator was incorrectly generating the `value` field of `PostV2ObjectsObjectRecordsValueTimestamp` as type `date` instead of `str`, even though the API returns full ISO 8601 timestamp strings like `"2025-10-01T07:10:52.888000000Z"`.

## Root Cause
The OpenAPI spec had the timestamp value field defined with:
- `type: string`
- `format: date-time`
- `x-speakeasy-type: date-time`

Speakeasy was interpreting the `format: date-time` and `x-speakeasy-type: date-time` fields to generate a Python `date` type, which cannot accept full datetime strings with time components.

## Solution
Changed the `value` field type from `date` to `str` in the following classes in `src/attio/models/post_v2_objects_object_recordsop.py`:

1. `PostV2ObjectsObjectRecordsValueTimestampTypedDict` (line 151)
2. `PostV2ObjectsObjectRecordsValueTimestamp` (line 168)

### Changes Made

#### File: `src/attio/models/post_v2_objects_object_recordsop.py`

**Line 151** - Changed from:
```python
value: date
```
To:
```python
value: str
```

**Line 168** - Changed from:
```python
value: date
```
To:
```python
value: str
```

## Testing
Verified the fix using the test script `test_unmarshal.py` which unmarshals the example.json response. The unmarshalling now succeeds:

```
✓ Unmarshalling successful!
Result type: <class 'attio.models.post_v2_objects_object_recordsop.PostV2ObjectsObjectRecordsDataResponse'>
```

## Note on Overlay
An attempt was made to fix this at the spec level using `overlay.yaml` to remove the `format` and `x-speakeasy-type` fields, but the overlay syntax did not work as expected. The fix was applied directly to the generated Python models.

## Impact
This change allows the SDK to correctly parse API responses containing timestamp values in record objects, enabling the `post_v2_objects_object_records()` method to work correctly with the returned data.

# SDK Changes for Nullable GET Query Params (None vs UNSET)

## Problem
Several GET operations declare nullable query parameters (`schema.type:
["string","null"]`). Speakeasy therefore generates these as three-state fields
(`OptionalNullable[T] = UNSET`): `UNSET` means "omit the param", while an
explicitly-passed `None` means "send an empty value" (e.g. the `assignee` param
documents "Pass an empty value or the string `null` to find tasks with no
assignee").

The generated operation call sites all pass `allow_empty_value=None`. The query-param builder (`utils/values.py::_is_set` / `utils/forms.py::_populate_form`)
treats `None` the same as `UNSET` ("not set") and drops the param. So passing
`assignee=None` produced a request with NO `assignee` param, returning ALL
tasks (assigned and unassigned) instead of only unassigned tasks. The
nullable-aware `serialize_model` that preserves explicit `None` is never
reached on the query-param HTTP path.

## Solution
Wire `allow_empty_value=["assignee"]` at the `tasks.get_v2_tasks` call sites so
the runtime's existing mechanism (`utils/queryparams.py`) sends an empty value
(`assignee=`) for an explicitly-set `None` while still omitting the param for
`UNSET`. The runtime already handles this correctly when the field name is
listed in `allow_empty_value`; it was simply never switched on.

Only `assignee` is wired this way. The other nullable GET query params
(`sent_after`, `sent_before`, `ends_from`, `starts_before`, `created_after`) are
timestamp filters whose OpenAPI descriptions only accept a timestamp string and
do not document an empty/null filter; sending `param=` for those would be an
invalid request, so `None` keeps the omit-the-param behavior for them.

### Affected operations
- `tasks.get_v2_tasks` / `get_v2_tasks_async` -> `allow_empty_value=["assignee"]`
  (`assignee` documents "Pass an empty value or the string `null` to find tasks
  with no assignee").

### Changes Made
- `src/attio/tasks.py` (2 call sites): changed `allow_empty_value=None` to
  `allow_empty_value=["assignee"]` for `get_v2_tasks` / `get_v2_tasks_async`.
- `overlay.yaml`: added `x-speakeasy-allow-empty-value: true` to the nullable
  `assignee` query parameter so the next `speakeasy run` regenerates the same
  wiring (durable, generation-layer fix). Speakeasy's Python generator reads the
  `x-speakeasy-allow-empty-value` extension
  (`internal/extensions/extensions.go::ExtAllowEmptyValue`) rather than the
  standard OpenAPI `allowEmptyValue` field, so the extension form is required for
  the wiring to survive regeneration.

## Note on Overlay
The overlay entry (`x-speakeasy-allow-empty-value: true`) is the durable,
generation-layer fix per the recommended approach. Because `speakeasy` was
unavailable to regenerate in the fixing environment, the matching change was
also applied directly to the generated call sites and is tracked here. After the
next `speakeasy run`, verify `git diff src/attio/tasks.py` shows the
`allow_empty_value=["assignee"]` wiring; if the generator does not emit it from
`x-speakeasy-allow-empty-value`, re-apply the call-site edit documented here.

## Testing
`tests/test_nullable_query_params.py` exercises the `tasks` operation (sync +
async) end-to-end with a mocked httpx transport, asserting:
- `assignee=None` -> `assignee=` sent empty
- `assignee` omitted (`UNSET`) -> param omitted
- a real value -> param sent with the value
- two-state `Optional[X]=None` sibling fields are still omitted (no regression)
- the timestamp-filter operations (`emails`, `meetings`, `threads`) keep the
  omit-on-`None` behavior (an empty value is not a valid filter for them)

Run with `uv run pytest tests/test_nullable_query_params.py -v`.

## Impact
Passing `None` for `assignee` now filters for unassigned tasks on the wire
(`assignee=`) instead of silently returning a superset of results. The nullable
timestamp filters (`sent_after`, `sent_before`, `ends_from`, `starts_before`,
`created_after`) are intentionally not wired for empty values — their contract
only accepts a timestamp string, so `None` keeps omitting the param.
